Sumário executivo
O arquivo implementa um boss completo com FSM, entidades projetadas e sistema visual pixel-art. O código funciona e está bem documentado, mas apresenta sete pontos de melhoria distribuídos em três categorias: performance, robustez e legibilidade.

1. Performance

1.1  Set _anchored recriado a cada frame
O set de estados ancorados é alocado dentro de update(), gerando uma nova estrutura em memória a cada tick (~60x/s). Como o conteúdo é fixo, deve ser uma constante de classe com frozenset.

Arquivo: stone_golem_boss.py — método update()
# Antes (problema)
def update(self, dt, player_x, player_y):
    _anchored = {"CHARGE", "FIRE", "EARTH_SHAKE",
                 "EARTH_PULL", "EARTH_ORBIT", ...}  # novo set a cada tick!
# Depois (correção)
class StoneGolemBoss:
    _ANCHORED_STATES = frozenset({
        "CHARGE", "FIRE", "EARTH_SHAKE",
        "EARTH_PULL", "EARTH_ORBIT", "EARTH_FIRE",
        "ORB_SPAWN", "ORB_HOLD", "ORB_FIRE",
        "SWEEP_CHARGE", "SWEEP_FIRE",
    })


1.2  getattr(Config, ...) chamado toda frame em RockShard
RockShard.update() acessa Config via getattr a cada chamada. As dimensões da tela não mudam em runtime — cachear no __init__ elimina o custo de reflexão repetida.

Arquivo: stone_golem_boss.py — classe RockShard
# Antes (problema)
def update(self, dt):
    screen_h = getattr(Config, "SCREEN_HEIGHT", 800)  # toda frame
    screen_w = getattr(Config, "SCREEN_WIDTH", 480)   # toda frame
# Depois (correção)
def __init__(self, x, y, angle_deg, ...):
    self._screen_w = getattr(Config, "SCREEN_WIDTH", 480)
    self._screen_h = getattr(Config, "SCREEN_HEIGHT", 800)

2. Robustez

2.1  Sentinela px == 0 em _draw_sweep_beam
Linha 960 usa px == 0 para detectar ausência de beam. Se o boss estiver em x=0 (borda esquerda), o beam não é desenhado silenciosamente. Verificar None é o padrão correto.

Arquivo: stone_golem_boss.py — método _draw_sweep_beam
# Antes (problema)
px, py, ex, ey = self.get_sweep_beam() or (0, 0, 0, 0)
if px == 0:  # falha se boss estiver em x=0
    return
# Depois (correção)
beam = self.get_sweep_beam()
if beam is None:
    return
px, py, ex, ey = beam


2.2  if ao invés de elif em _change_fsm
Os 10+ blocos condicionais em _change_fsm são mutuamente exclusivos — cada transição ativa exatamente um estado. Usar elif em vez de if documenta essa intenção e evita avaliar condições desnecessárias após o primeiro match.

Arquivo: stone_golem_boss.py — método _change_fsm
# Antes (problema)
if new_state == "CHARGE":
    self._charge_particles.clear()
if new_state == "FIRE":      # ainda avaliado mesmo após match acima
    self._fire_shots_count = 0
if new_state == "ORB_SPAWN": # idem
    ...
# Depois (correção)
if new_state == "CHARGE":
    self._charge_particles.clear()
elif new_state == "FIRE":    # para no primeiro match
    self._fire_shots_count = 0
elif new_state == "ORB_SPAWN":
    ...



3. Legibilidade e manutenibilidade

3.1  Números mágicos sem nome
Valores como 150 (max partículas), 0.4 (chance de trail) e 800 (fade speed) aparecem inline. Ao extrair como constantes de classe, o balanceamento de gameplay fica centralizado e autoexplicativo.

Arquivo: stone_golem_boss.py — classes OrbitalRock e StoneGolemBoss
# Antes (problema)
if len(self._charge_particles) < 150:
    ...
if random.random() < 0.4:
    self.trail.append([self.x, self.y, 255.0])
t[2] -= 800 * dt
# Depois (correção)
class OrbitalRock:
    TRAIL_SPAWN_CHANCE = 0.4
    TRAIL_FADE_SPEED   = 800.0

class StoneGolemBoss:
    MAX_CHARGE_PARTICLES = 150


3.2  Alias Boulder sem documentação
A linha Boulder = GolemMine não tem comentário. Sem contexto, é impossível saber se é legado, alias intencional ou erro. Usar TypeAlias com comentário comunica a intenção diretamente.

Arquivo: stone_golem_boss.py — linha 204
# Antes (problema)
Boulder = GolemMine  # sem contexto
# Depois (correção)
from typing import TypeAlias

# Alias de compatibilidade — EntityManager referencia o nome Boulder
Boulder: TypeAlias = GolemMine


3.3  _run_fsm monolítico e __init__ extenso
_run_fsm tem ~150 linhas tratando todos os estados em sequência. Extrair cada handler para um método próprio (_fsm_scan, _fsm_charge, etc.) torna cada estado testável de forma isolada. O mesmo vale para o __init__ de StoneGolemBoss: dividir em _init_stats(), _init_fsm() e _init_surfaces() facilita rastrear onde um atributo é inicializado.

Arquivo: stone_golem_boss.py — métodos _run_fsm e __init__
# Antes (problema)
def _run_fsm(self, dt, px, py, mines, shards):
    if state == "SCAN":
        ...  # 10 linhas
    elif state == "OPENING":
        ...  # 8 linhas
    # ... +130 linhas
# Depois (correção)
def _run_fsm(self, dt, px, py, mines, shards):
    handler = getattr(self, f'_fsm_{self.fsm_state.lower()}', None)
    if handler:

def _fsm_scan(self, dt, px, py, mines, shards):
    self._move_vertical(dt)
    self.eye_growth = 0.0

def __init__(self, x, y, health=None, difficulty_multiplier=1.0):

Bônus: consistência de interface
O módulo documenta que todas as entidades expõem .rect, .dead e .causes_damage — mas a implementação é inconsistente:

•	GolemMine: causes_damage é atributo de instância (sempre True)
•	OrbitalRock: causes_damage é @property (condicional)
•	RockShard: causes_damage não está implementado

Solução recomendada: formalizar um typing.Protocol com os três atributos e anotar as listas internas de entidades com esse tipo.

Protocolo sugerido — entities/protocols.py
# Antes (problema)
# Sem contrato formal — qualquer entidade pode faltar um atributo
# e o erro só aparece em runtime durante uma colisão
# Depois (correção)
from typing import Protocol
import pygame

class DamageEntity(Protocol):
    rect: pygame.Rect
    dead: bool

    @property
    def causes_damage(self) -> bool: ...

# Em playing.py:
def _check_ship_damage(self, entities: list[DamageEntity]) -> None:
    ...
