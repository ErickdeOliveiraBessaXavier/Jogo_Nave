# Análise Técnica do Projeto Space Shooter

Após revisar todos os arquivos, o projeto está bem estruturado para um jogo Pygame. Abaixo estão os pontos organizados por prioridade.

---

## 🔴 Alta Prioridade

### 1. `entity_manager.py` — Recriação de listas a cada frame

```python
# cleanup() faz isto em todo frame:
self.bullets = [b for b in self.bullets if not b.dead]
self.alien_bullets = [b for b in self.alien_bullets if not b.dead]
# ... ~15 listas
```

**Problema:** list comprehensions criam novas listas a cada frame, gerando pressão no garbage collector. Com 20+ listas, o custo acumula.

**Solução:** filtrar in-place com swap de índice ou usar `collections.deque` com remoção O(1) para listas de curta duração. Para listas grandes (bullets, enemies), uma abordagem eficiente é:

```python
# Em vez de reconstruir, filtrar in-place
def _filter_dead_inplace(lst: list) -> None:
    i = 0
    while i < len(lst):
        if lst[i].dead:
            lst[i] = lst[-1]
            lst.pop()
        else:
            i += 1
```

> **Cuidado:** essa abordagem não preserva ordem. Se a ordem de renderização importar para alguma lista, use apenas onde a ordem é irrelevante (bullets, explosions, etc.).

### 2. `collisions.py` — `_get_enemy_collision_mask_data` chamado repetidamente

```python
# Chamado por frame para cada projétil × cada inimigo candidato
mask_data = cls._get_enemy_collision_mask_data(enemy)
```

**Problema:** usa `getattr` com fallbacks encadeados em hot path. Inimigos sem máscara percorrem toda a cadeia a cada checagem.

**Solução:** cachear o resultado por `id(enemy)` com invalidação quando `enemy.dead = True`, ou adicionar um atributo `_has_pixel_mask: bool` nas entidades durante `__init__`.

### 3. `playing.py` — `_batch_floating_scores` é O(n²)

```python
# O comentário no código admite isso:
# Agrupa score events próximos num único evento somado (O(n²) intencional)
for i, (x1, y1, pts1) in enumerate(score_events):
    for j, (x2, y2, pts2) in enumerate(score_events):
```

**Problema:** com explosões em área (AirStrike, BlackHole) destruindo 15-20 inimigos simultaneamente, isso roda 225-400 iterações por frame nesse momento específico.

**Solução simples:** limitar o processamento ou usar grid espacial simples:

```python
# Limite prático: se poucos eventos, o custo é desprezível
if len(score_events) <= 8:
    return self._batch_floating_scores_quadratic(score_events)
# Para muitos, apenas agrupar por célula de grid fixo
cell_size = proximity_threshold
buckets: dict[tuple[int,int], list] = {}
for x, y, pts in score_events:
    key = (int(x // cell_size), int(y // cell_size))
    buckets.setdefault(key, []).append((x, y, pts))
```

## 🟡 Média Prioridade

### 4. `renderer.py` — StarField recria pontos do polígono a cada frame

```python
def draw(self, surface):
    for s in self.stars:
        # Calcula pontos do polígono a cada frame para estrelas grandes
        while t < self.TWO_PI:
            x = a * (math.cos(t) ** 3)  # cubo de cos/sin
            y = a * (math.sin(t) ** 3)
            points.append(...)
            t += step  # 20 iterações por estrela grande
```

**Problema:** estrelas grandes (size 2 ou 3) recalculam 20 pontos trigonométricos por frame. Com 30 estrelas, muitas podem ser grandes.

**Solução:** pré-calcular os pontos unitários uma vez e escalar:

```python
# No __init__ do StarField:
_UNIT_STAR_POINTS = [
    (math.cos(t)**3, math.sin(t)**3)
    for t in (i * TWO_PI / 20 for i in range(20))
]

# No draw, apenas escalar:
points = [(cx + a*px, cy + a*py) for px, py in _UNIT_STAR_POINTS]
```

### 5. `meta_progression.py` — `PlayerProfile.save()` serializa tudo sempre

```python
def save(self):
    # Serializa TODOS os level_stats, sessions, upgrades, etc.
    # Chamado a cada 5 níveis, ao fim de sessão, e por auto_save
```

**Problema:** para perfis com muitos níveis jogados (50+), a serialização completa a cada save pode causar um pequeno freeze perceptível, especialmente em hardware lento.

**Sugestão:** implementar save incremental — marcar apenas as seções `_dirty` individualmente (level_stats dirty, session dirty, etc.) e serializar só o que mudou. Alternativamente, mover o save para uma thread separada com `threading.Thread(target=self._write_json, daemon=True)`.

### 6. `backgrounds.py` — `CityBackground._draw_windows` limpa o cache periodicamente de forma imprecisa

```python
# Limpar cache periodicamente para economizar memória
if int(self.blink_timer * 100) % 500 == 0:
    self.blink_pattern_cache.clear()
```

**Problema:** essa condição pode ser verdadeira por vários frames consecutivos (enquanto `blink_timer * 100` for múltiplo de 500), causando limpezas em rajada. Além disso, o cache pode crescer indefinidamente entre as limpezas — `window_key` é `wx + wy`, podendo colidir para janelas diferentes.

**Correção:**

```python
# Usar um flag de limpeza por intervalo fixo de tempo:
self._cache_clear_timer += dt
if self._cache_clear_timer > 5.0:
    self.blink_pattern_cache.clear()
    self._cache_clear_timer = 0.0

# E usar chave sem colisão:
window_key = (wx, wy)  # tupla em vez de wx + wy
```

### 7. `spawner.py` — `_count_enemies_by_type` chamado múltiplas vezes por frame

```python
def update(self, dt, entity_manager, ...):
    counts = self._count_enemies_by_type(entity_manager)  # 1x
    
    self._update_weighted_enemy_spawn(dt, ..., counts=counts)  # passa counts
    self._update_mine_spawner(dt, ...)  # NÃO recebe counts — chama internamente?
```

**Verificação:** `_update_mine_spawner` e `_update_propeller_spawner` não recebem `counts`, mas `_should_spawn_enemy` chama `_count_enemies_by_type` internamente se `counts=None`. O counts calculado no topo do `update` não é repassado a todos os sub-métodos, potencialmente causando recontagens. Passar `counts` como parâmetro para todos os submétodos que chamam `_should_spawn_enemy` eliminaria isso.

## 🟢 Baixa Prioridade / Qualidade de Código

### 8. `music_manager.py` — Muita repetição no padrão de play por boss

Cada boss tem um método idêntico com apenas o nome da chave diferindo:

```python
def play_spike_boss_music_internal(self) -> None:
    music_path = get_resource_path(os.path.join(..., str(self._music_paths()["spike_boss"])))
    if os.path.exists(music_path) and self.sound_manager.current_music != "spike_boss":
        self._transition_to_music(music_path, "spike_boss")

def play_slime_boss_music_internal(self) -> None:
    # Idêntico, só muda "slime_boss"
```

**Solução:** um único método genérico:

```python
def _play_boss_music_by_key(self, key: str) -> None:
    music_path = get_resource_path(
        os.path.join(str(SOUND_PATHS["base"]), str(self._music_paths()[key]))
    )
    if os.path.exists(music_path) and self.sound_manager.current_music != key:
        self._transition_to_music(music_path, key)
```

Isso reduz ~70 linhas para ~10 e facilita adicionar novos bosses.

### 9. `levels.py` — `LevelConfig` é recriada como cópia em cada pipeline stage

```python
# _apply_theme_enemy_eligibility, _apply_theme_enemy_weights,
# _apply_stage_progression_enemy_weights, _apply_enemy_variety_cap
# — cada um cria um novo LevelConfig se algo mudou
return LevelConfig(
    level_number=config.level_number,
    enemy_spawn_config=adjusted_spawn_config,
    # ... todos os campos copiados manualmente
)
```

**Problema:** `LevelConfig` é um `@dataclass` — use `dataclasses.replace()`:

```python
from dataclasses import replace

return replace(config, enemy_spawn_config=adjusted_spawn_config)
```

Mais seguro (não esquece campos novos) e menos verboso. Já é usado em `spawner.py`, então o padrão existe no projeto.

---

### 10. `spatial_grid.py` — `insert_batch` existe mas raramente é usado

O `EntityManager.rebuild_all_grids` faz inserções individuais em loop:

```python
for e in self.enemies:
    if not e.dead:
        self.enemy_spatial_grid.insert_from_rect(e)
```

Usar `insert_batch` com a lista pré-filtrada seria mais eficiente, pois evita overhead de chamada de método por elemento.

## ✅ O que está bem feito

- **Object Pooling** (`MeteorPool`, `BulletPool`, `ExplosionPool`, `RockGliderPool`) — excelente para jogos 2D
- **Spatial Grid** para colisões — escala bem com muitos inimigos
- **`@lru_cache`** em assets e fontes — correto
- **`dataclasses.replace`** em `spawner.py` — bom padrão
- **Separação de responsabilidades** entre `MusicManager`/`SfxManager`/`SoundManager`
- **`TransitionPhase` como Enum** em `playing.py` — elimina flags booleanos conflitantes
- **`HitResult` imutável** com `NO_HIT` singleton para hot path — excelente padrão

O projeto está em boa forma. Os itens 1, 2 e 5 são os que teriam o impacto mais perceptível se corrigidos.
