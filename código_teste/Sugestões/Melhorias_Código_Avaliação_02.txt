# Code Review: Event Bus Implementation

## Avaliação Geral

A implementação mostra intenção correta, mas a execução tem problemas sérios que precisam ser corrigidos antes de considerar isso "resolvido". Vou ser direto.

---

## 🔴 Problemas Críticos

### 1. Duplicação de Efeitos — O Bug Mais Sério

Em `effects_system.py`, o handler `_on_enemy_destroyed` cria uma explosão para cada inimigo destruído. Mas em `collisions.py`, o método `_apply_hit` já cria explosões via `entity_manager.spawn_explosion(...)`:

```python
# collisions.py — já cria explosão
def _apply_hit(self, ...):
    if result.explosion_size > 0:
        entity_manager.spawn_explosion(hit_x, hit_y, ...)  # Explosão #1

# effects_system.py — cria OUTRA explosão via evento
def _on_enemy_destroyed(self, event: events.EnemyDestroyed) -> None:
    self._entity_manager.spawn_explosion(...)  # Explosão #2 (duplicada!)
```

O evento `EnemyDestroyed` não está sendo emitido em nenhum lugar do código atual — então a duplicação ainda não se manifesta. Mas assim que for conectado corretamente, cada morte de inimigo gerará duas explosões. Isso revela que o EventBus foi implementado **sem remover o comportamento original**, criando uma arquitetura inconsistente.

**Regra fundamental violada**: ao mover responsabilidade para um handler de evento, o comportamento original deve ser removido do local anterior. Isso não foi feito.

## 🟠 Problemas Graves de Arquitetura

### 5. EventBus Não Tem `off()` — Memory Leak Garantido

```python
class EventBus:
    def on(self, event_type, fn): ...
    def emit(self, event): ...
    def clear(self): ...  # Nuclear — remove TUDO
```

Não existe `off(event_type, handler)`. Se uma cena se registra no EventBus e depois é destruída, os handlers ficam referenciando objetos mortos. O método `clear()` é uma solução nuclear que exige reregistro de todos os sistemas — impraticável numa arquitetura real com hot-reload de cenas.

A solução adequada:

```python
def off(self, event_type: Type[T], fn: Callable[[T], None]) -> None:
    handlers = self._subscribers.get(event_type, [])
    try:
        handlers.remove(fn)
    except ValueError:
        pass
```

E os sistemas devem ter `cleanup()` funcional:

```python
class SoundSystem:
    def cleanup(self) -> None:
        self._bus.off(events.PlayerShot, self._on_player_shot)
        self._bus.off(events.EnemyDestroyed, self._on_enemy_destroyed)
        # ...
```

O `cleanup()` atual em `sound_system.py` tem um comentário dizendo que não funciona. Isso é technical debt admitido na entrega.

### 6. `SoundSystem._on_enemy_destroyed` Chama o Som Errado

```python
def _on_enemy_destroyed(self, event: events.EnemyDestroyed) -> None:
```

`SoundManager` não tem `play_explosion()` — tem `play_explosion_asteroid()`, `play_explosion_alien()`, `play_explosion_boss()`. O método genérico não existe. Isso provavelmente lança `AttributeError` silenciado pelo decorator `@require_audio`.

### 7. `EnemyDestroyed` Nunca é Emitido

Procurando em todo o codebase, `events.EnemyDestroyed` é definido mas não é emitido em lugar nenhum. O `SoundSystem` se registra para ouvir esse evento, mas ele nunca chega. Isso significa que `_on_enemy_destroyed` e `_on_boss_defeated` no `SoundSystem` são código morto.

O fluxo correto exigiria emissão em `collisions.py` dentro de `_apply_hit` quando `result.killed == True`, mas isso não foi implementado.

## 🟡 Problemas de Design

### 10. Eventos Assimétricos — Metade do Sistema Ainda é Imperativo

A implementação é parcial por design. Alguns sons usam eventos, outros não. Não há consistência. Isso é pior do que não ter EventBus, porque agora existem dois sistemas paralelos com comportamento undefined quando ambos disparam.

Se o EventBus não substitui completamente o acoplamento direto, ele apenas adiciona complexidade sem benefício.

---

### 11. `SpawnFloatingScore` Viola Single Responsibility

O evento carrega responsabilidade de renderização (cor do texto). Eventos devem transportar dados de domínio, não decisões visuais. A cor deveria ser determinada pelo sistema de renderização com base no tipo de evento ou contexto, não ser hardcoded no ponto de emissão.

---

### 12. `game_events.py` Tem Eventos Sem Uso Imediato

`LevelCleared`, `ScoreGained`, `GameStateChange` são definidos mas não emitidos nem consumidos. Isso não é problema em si, mas combinado com `EnemyDestroyed` que também não é emitido, sugere que a lista de eventos foi expandida especulativamente sem completar a implementação dos casos de uso reais.

## O Que Precisa Ser Feito Para Resolver Corretamente

1. **Implementar `off()` no EventBus** antes de qualquer uso em produção
2. **Remover o comportamento original** ao mover responsabilidade para handlers — escolha um caminho ou o outro, nunca os dois
3. **Emitir `EnemyDestroyed`** em `collisions._apply_hit` quando `result.killed` for `True`, passando o `enemy_type` correto
4. **Corrigir métodos inexistentes** em `SoundSystem` (`play_explosion`, `set_music_state`, `play`)
5. **Remover explosão duplicada** do `_on_boss_defeated` ou remover as explosões de `_end_boss_fight` e centralizar no handler
6. **Implementar `cleanup()`** em `SoundSystem` e `EffectsSystem` usando `off()`
7. **Auditar todos os pontos de emissão** para garantir que o comportamento original foi removido

A arquitetura do EventBus é correta como direção. A execução precisa de uma segunda iteração completa.
